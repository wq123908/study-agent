# 阶段 13 学习记录

阶段主题为独立运行记录与结构化任务契约。文档准备于 2026-11-27，当前状态为 **文档已就绪，代码待开始**。

## 目标与全局位置

V1.0 的 `SessionState` 保存一个会话的消息、摘要与待审批信息。V2.0 需要同时描述一次任务从接收到结束的全过程，让调用方能按运行标识查询状态、关联结果和追踪。

```text
一个会话 session_id
    ├── 第一次请求 → run_id A → 输入、执行阶段与结果
    └── 第二次请求 → run_id B → 输入、执行阶段与结果

阶段 13 定义这些数据
    ↓
阶段 14 负责保存、查询、等待和恢复
    ↓
阶段 15–17 接工具策略、编排与结果验证
    ↓
阶段 18 接入 CLI、Web 和 HTTP
```

本阶段先完成数据模型和序列化，随后再逐阶段把它们接到实际执行入口。执行阶段中的完成表示程序正常走到终点，任务结果仍可能因成功条件未满足而判定为失败。

## 13.1 独立运行记录

### 原理与已有代码

先读 `agent/state.py`、`Agent._guarded_run()` 和 `Agent.resume()`。现有的 `RunStatus` 取值为 `IDLE` 和 `WAITING_APPROVAL`，被 `SessionState` 使用。新运行类型建议使用 `RunPhase`，与既有类型并列演进。

| 标识 | 含义 |
| --- | --- |
| `session_id` | 关联多轮对话与记忆的会话标识。 |
| `run_id` | 一次任务的稳定标识，暂停后恢复仍关联原运行。 |
| `trace_id` | 一次执行或恢复尝试的诊断追踪标识，可以关联同一个运行。 |

### 建议模块

首个模块为 `agent/run_state.py`，建议定义 `RunPhase` 和 `RunRecord`。命名可依据实际实现调整，并同步记录原因。

- `RunPhase` 表达已创建、运行中、等待中、已完成、失败和取消等执行阶段。状态转移的规则在阶段 14 接入。
- `RunRecord` 首批字段为 `run_id`、`session_id`、`phase` 和 `created_at`，使用独立的默认值生成方式。
- `to_record()` 导出 JSON 可编码的数据，`from_record()` 从记录恢复对象。
- 只有新建运行时生成新 ID。读回旧记录时使用原 ID、时间和阶段。
- 两条运行保持各自的标识与阶段，修改一条记录后另一条记录保持自身值。

### 带写顺序

1. **13.1a** 讲清三个标识和两个状态对象，给枚举与记录字段的完整代码。随即导入模块，创建两条同会话记录并检查 ID 不同。
2. **13.1b** 加入序列化和反序列化，解释枚举值、时间戳和 ID 的保存方式。
3. **13.1c** 给离线断言，验收同一会话的两条独立运行和 JSON 往返。

每轮生成的代码控制在 60 行以内。首轮由 Gemini 针对实际构造签名给出可运行命令，用户录入后执行。

### 预期验收

- 创建 `session_id` 相同的两条运行，`run_id` 不同。
- 调整第一条的 `phase`，第二条仍保持原阶段。
- 导出记录经过 JSON 编码、解码再加载，原 ID、会话关联、阶段和时间保持一致。
- 缺失关键标识或无效阶段给出明确错误，防止静默恢复成一条新运行。
- 用正确解释器导入新模块，结果不依赖模型服务。

## 13.2 结构化任务输入

### 目标和模块

建议新增 `agent/task.py`，定义 `TaskRequest`。输入包括会话关联、文本或结构化参数，以及必要的请求元数据。执行身份通过后续运行上下文和权限策略取得。

先复用现有 Pydantic 能力确定校验方式，再说明数据怎样传给阶段 14 的运行入口。当前 `app/schemas.py` 保留既有 HTTP 模型，统一 HTTP 映射在阶段 18 实现。

### 学习知识点

- 任务请求与对话消息的不同职责。
- 输入合法性、JSON 可编码性和额外字段处理。
- 不可变标识、请求参数和运行时依赖的不同生命周期。
- 后续从 CLI、HTTP 或其他调用方映射到同一任务输入的方式。

### 预期验收

合法的文本任务与结构化参数可以编码并读回。空输入、错误字段类型和无法编码的值按既定契约处理。新建运行时将请求关联到原会话，保留两条任务各自的数据。

## 13.3 任务结果与产物引用

### 目标和模块

建议新增 `agent/result.py`，定义 `TaskResult` 和 `ArtifactRef`。结果可携带文本、结构化数据、错误及产物引用，能关联所属运行。产物先描述标识、类型及定位信息，具体文件存储适配在后续实际需求中接入。

执行阶段描述程序走到哪里，任务结果描述是否满足成功条件。回复评分留给阶段 17，具有独立的维度与证据。

### 学习知识点

- 执行终止、任务成功、部分完成、失败与待核对之间的关系。
- 结果中使用结构化错误，保留失败来源。
- 产物引用与正文数据的职责，后续由访问策略控制读取。
- 成功条件由任务配置，数据契约提供表达和校验方式。

### 预期验收

构造并序列化一条成功结果、一条失败结果和一条待核对结果。表达“程序已执行到末尾、任务失败”的场景，并关联原 `run_id`。结果包含两个不同类型的产物引用时可以完整读回，矛盾状态按契约拒绝或明确处理。
